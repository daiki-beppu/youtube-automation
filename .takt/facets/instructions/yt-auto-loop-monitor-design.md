design_review → design_fix のループが {cycle_count} 回繰り返されました。

Report Directory 内の設計レビューレポート 3 種（設計 / 規約整合性 / テスト設計）と、実装計画・テスト設計レポートを確認し、このループが健全（収束傾向）か非生産的（発散・振動）かを判断してください。

**判断基準:**

- 同一 `finding_id` が複数サイクルにわたって `persists` しているか
  - 同一 `finding_id` が繰り返し persists → 非生産的（スタックしている）
  - 前回の finding が resolved され、ブロッキングの finding が総量として減っている → 健全（収束傾向）
  - resolved は進むが、毎サイクル同数以上の新規指摘が湧いて総量が減らない → 非生産的の疑い。新規指摘が「成果物の無効化」の根拠（反例・観測）を持つかを確認する。根拠のない新規指摘での REJECT が続いているなら、それは収束ポリシー違反のレビューであり、設計側の問題ではない
- 設計レポートの修正が、指摘に対する実質的な変更になっているか
  - 文言だけ変えて構造が変わっていない → 非生産的
- 規約整合性レビューが `NEEDS_CONVENTION_REVISION` を繰り返しているか
  - 繰り返している場合、逸脱の正当性と規約文書の改訂案が計画に書かれているかを確認する。書かれているのに差し戻され続けているなら、判定側の要求が過剰である可能性がある → **計画へ差し戻す**（改訂案を含めた再計画で打開できる）
- 要件 ID の数や内容が毎サイクル変わっているか
  - 変わり続けている → 要件そのものが固まっていない。**計画へ差し戻す**（intake のブリーフから要件を立て直す必要がある）
- 指摘件数が全体として減少傾向にあるか

**この step はまだコードを書いていない段階であることに注意してください。** 設計段階の差し戻しは実装後の手戻りより桁違いに安いため、判断は慎重側に倒してよい。ただし、同じ論点が 3 周しても収束しないなら、それは設計レビューで解ける問題ではなく計画の前提が誤っている。

打ち切りではなく計画への差し戻しを優先してください。設計段階での ABORT は、intake が通した issue を実質的に否定することになるため、計画の作り直しでも打開できないと判断できる場合だけにしてください。
