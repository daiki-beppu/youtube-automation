直前の intake が出力した**実装ブリーフ**を読み、リファクタリングの計画を立ててください。ブリーフは**この指示に添えられた直前の出力**として渡されています。**`intake-brief.md` をファイルとして探さないでください** — intake は callable sub-workflow であり、そのレポートは子の report namespace に置かれるため、この step の Report Directory には存在しません（docs/takt-operations.md）。**この step ではコードを書きません。**

リファクタリングの計画は「何を変えるか」より先に**「何を変えないか」を確定する**ことが核です。維持すべき外部契約が列挙されていない計画は、挙動変更の混入を検出できません。壊れていないものを壊さず構造だけを良くする — それを検証可能にするのがこの計画の仕事です。

## 手順

1. **ブリーフの読み込み**: ブリーフの「確定している決定」「要件候補」「対象外」「制約」を読む。ブリーフに書かれていない要求を足さない
2. **対象の現状把握**: 対象モジュールを Read / Grep で読み、公開面（公開関数・クラス・entry point・呼び出し元）を実際に走査する。対象範囲の既存テストを実行して現状 green を確認する:
   ```
   nix develop --command uv run pytest tests/<対象範囲> -q
   ```
   red がある、または issue の記述から対象が既に壊れていると分かったら **ABORT**（リファクタリングではなくバグ修正が必要。auto-fix へ）
3. **維持契約の列挙**: 変更対象が触れる外部契約を、種類ごとに漏れなく列挙する:

| 種類                 | 走査方法                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| 公開 CLI             | `pyproject.toml` の `[project.scripts]` にある `yt-*` コマンドの引数・出力。対象モジュールを entry point から辿る |
| config スキーマ      | `config/channel/*.json` の形。`configuration/` の dataclass と `_REQUIRED_KEYS_BY_SECTION`               |
| skill 配布物         | `.claude/skills/` の構成と、skill が呼ぶスクリプト・CLI のインターフェース                               |
| 例外型               | `infrastructure/errors.py` のドメイン例外の型と発生条件（呼び出し元が catch している型を変えない）       |
| テストが担保する挙動 | 対象モジュールを import / 実行している `tests/` の既存テストが固定している挙動                           |

4. **担保テストの確認**: 各契約について、それを担保する既存テストの有無を `rg` で確認し、実在パスまたは「なし → safety_net で追加」を記録する
5. **要件 ID の採番**: 「リファクタ後も X が変わらない」を要件として `REQ-<issue番号>-<2桁連番>` を振る。リファクタの動機（解消する観測可能な問題）も要件化する。Policy の採番規則に従う。ここで振った ID は後段で不変
6. **リファクタ方針**: 何をどう変えるか / 何を変えないかを書く。変更の動機は**観測可能な問題**（file:line で示せる重複・結合・障害・テスト困難の実例）であること。推測の技術的負債（「いずれ問題になりそう」）を動機にしない
7. **規約逸脱の事前申告**: 方針が規約文書（リポジトリルートの `CLAUDE.md` / `docs/development.md` / `docs/skill-design/skill-authoring-guidelines.md` / 有効 ADR）の決定から外れるなら、逸脱点・技術的正当性・規約文書の改訂案を申告する。**黙って逸脱しない**
8. **スコープの確定**: やらないこと（今回変えないモジュール・「ついで」に見える改善）を明示する。1 PR でレビューできる大きさを超えるなら分割し、後続分はスコープ外に記録する

## 制約

- コードを書かない（計画レポートの出力のみ）
- 外部挙動の変更を方針に含めない。「この際この挙動も直す」が必要に見えたら、それはこのレーンの対象外（auto-feature / auto-fix の仕事）
- パッケージ操作・コマンド実行は Policy のツールチェーンポリシーに従って記述する

## 判定

**これは {step_iteration} 回目の計画です。作り直しの上限は 3 回です。** `{step_iteration}` が 4 以上なら、内容にかかわらず打ち切ってください。

計画のやり直しは複数方向から来ます — 計画レビューの `NEED_REPLAN`、計画修正（`plan_fix`）の上限到達・前提否定、リファクタ実装の「挙動を変えずには達成できない」・バグ発見、実装ゲートの `needs_replan`、最終ゲートの `need_replan`、`spillover` の引き戻し、loop monitor の判定。**どの経路で戻ってきても同じラウンドに数えます。**

- `{step_iteration}` が 4 以上 → **打ち切る**。各ラウンドで立てた方針と差し戻された理由を報告に残す
- 維持契約を列挙し、要件 ID を採番し、リファクタ方針を決めた → 計画レビューへ
- ユーザーが質問をしている（実装タスクではない）→ 完了
- 対象が既に壊れている → **ABORT**。観測した症状と auto-fix へ回すべき理由を報告に残す
- ブリーフの決定だけでは方針が一意に決まらない → ABORT し、何が決まれば進めるかを列挙する

やり直しのときは、**前回の計画レポートを読んでから始めてください。** 同じ方針を言い換えて再提出すると、同じ理由で差し戻されます。前回何が否定されたかを踏まえて方針を変えること。
