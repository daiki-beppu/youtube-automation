監査台帳の検収を行ってください。これは「台帳が Issue 化に足る完全性を持つか」の検収であり、コードレビューでも監査のやり直しでもありません。

**重要:** 監査計画を参照してください:

{report:01-unit-audit-plan.md}

**このステップでは、プロンプトに含まれる汎用 review policy の「APPROVE は issue 0 件」基準を適用しない。検収基準は本 instruction が唯一の正である。**

**承認基準（以下をすべて満たせば承認する。満たしたうえで残る軽微な改善余地は差し戻し理由にならない）:**

1. 進捗行が「本番 N/N・テスト M/M」に達し、Status が SCOPE_COMPLETE である
2. 本番コード台帳・テストファイル判定の表の実際の行数が、進捗行・集計と一致している。優先度別 Findings の集計が Findings セクションの `- 優先度:` フィールドの実数と一致している
3. Coverage が Partial / Missing の行に「未カバー内容」と対応 F 番号（または「追加不要（理由）」）が記載されている
4. すべての Finding が `### F-{3 桁連番}:` 見出し単位で、優先度・対象・現状・根拠・推奨対応・完了条件を備えている（1 行圧縮・範囲見出しは欠落として扱う）。F 番号が F-001 からの連番で欠番がない（取り下げは「（取り下げ）」見出しで残っていれば欠番ではない）
5. 実行証跡にスコープ確定コマンドと収集件数が記録され、集計と矛盾しない

**差し戻してよいのは上記 1〜5 の物理的な欠落・矛盾のみ。** 以下は差し戻し理由にしない（気づいた場合は応答内に「参考情報」として記録するだけにする）:

- 表現・言い回し・分類粒度の改善余地
- 追加の深掘り・網羅性向上の提案（スコープ表の全行が済である限り）
- テスト・ビルドの再実行やその証跡の不足
- 「自分ならこう判定する」という判定の相違（明白な事実誤認を除く）

**差し戻す場合は各指摘に SUP-{連番} の ID を付け、対象行・欠落フィールドを特定できる形で列挙する。** 同じ趣旨の指摘を言い換えて繰り返さない。

**応答の最後に、必ず次のどちらかを一字一句そのまま出力する（言い換え禁止。この宣言文がワークフローの遷移判定に照合される）:**

- 承認: 「監査が完全で Issue 化できる品質に達している」
- 差し戻し: 「カバレッジ監査が不完全、または根拠が不足している」
