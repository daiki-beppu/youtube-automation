Report Directory のゲート段レポート（feature では設計、fix では診断）が **本リポジトリの規約文書に整合しているか** だけをレビューしてください。コードはまだ存在しません。実装に入る前に規約違反を止めるのがこの step の役割です。

対象は呼び出し元の workflow によって変わります。Report Directory にあるものを読んでください。

| workflow       | 対象レポート                 | 照合する節                                                     |
| -------------- | ---------------------------- | -------------------------------------------------------------- |
| `yt-auto-feature` | `plan.md` + `test-design.md` | 「実装方針」「規約整合性の事前申告」                           |
| `yt-auto-fix`     | `diagnosis.md`               | 「原因」「修正方針」「回帰テスト設計」「規約整合性の事前申告」 |

他のレビュアーの有無を前提にしないでください。コーディング作法・テスト品質はこのレビューの担当外です。

## 手順

1. Knowledge の Source Path を Read で開き、**規約文書の本文を全文取得する**。要約や記憶で判定しない。検査対象はリポジトリルートの `CLAUDE.md`、`docs/development.md`、`docs/skill-design/skill-authoring-guidelines.md`、`docs/adr/` の有効 ADR（ADR-0013 = dashboard TS 例外、ADR-0021 = メンテナンスモード）
2. `docs/adr/` を Glob で確認し、Knowledge の索引にない有効 ADR が増えていないかを見る
3. 各規約文書の規範的な決定（「必ず〜する」「〜禁止」）を列挙する（取捨選択しない）
4. 列挙した決定を、設計レポートの方針（feature は「実装方針」、fix は「修正方針」）と 1 対 1 で照合する
5. 設計レポートの「規約整合性の事前申告」が、実際の方針と一致しているかを検証する。**申告漏れは違反として扱う**
6. 開発規約の個別項目に照合する: 設定アクセスが `load_config` 経由か（ハードコーディングがないか）、パッケージ内 import が fully-qualified（`from youtube_automation.xxx import ...`）か、エラーがドメイン例外（`infrastructure/errors.py`）か、新規 CLI が `yt-*` prefix + entry point 登録か、SKILL.md frontmatter の `description:` が double-quoted か、実コード変更に `CHANGELOG.md` の `[Unreleased]` 更新が伴うか
7. 新しく置く設定・データの SSOT が正しいか（チャンネル固有値が `config/channel/*.json` に集約されているか）を判定する
8. メンテナンスモード（ADR-0021）の範囲外の機能（dashboard/ + extensions/ 以外の新規 TS 実装、tayk core の復活など）が設計レポートに紛れ込んでいないかを確認する
9. **fix のときのみ**: バグの原因そのものが規約逸脱（ハードコーディングされたチャンネル固有値、`load_config` を迂回した設定アクセス、生の `Exception` / `KeyError` の catch、fully-qualified でない import など）であるかを判定する。逸脱が原因なら、その事実が「原因」の記述に含まれ、修正方針が逸脱の解消になっているかを確認する。**逸脱を残したまま症状だけ直す方針は「違反」として差し戻す**

**これは {step_iteration} 回目のレビューです。** 再走査の対象は **全規約文書の全決定**です。Policy の再走査ポリシーと収束ポリシーに従ってください（形式・記載整備の指摘は違反にせず「非ブロッキング指摘」へ）。

## 判定の 3 値

| 判定                                        | 条件                                                                                    |
| ------------------------------------------- | --------------------------------------------------------------------------------------- |
| 整合                                        | 規約文書の決定に沿っている                                                              |
| 要規約改訂（`NEEDS_CONVENTION_REVISION`）   | 逸脱に技術的正当性はあるが規約文書が未改訂、または計画の申告が不十分。**差し戻す**      |
| 違反                                        | 正当性のない逸脱、または正当性が示されていない逸脱。**差し戻す**                        |

## 禁止

- 規約文書に書かれていない設計上の好みを指摘すること
- 規約文書の本文を引用できない指摘を出すこと
- 「既存コードがそうなっている」を正当性として受け入れること
- TS 版（tayk 別リポジトリ）の実装との差分を根拠にすること
