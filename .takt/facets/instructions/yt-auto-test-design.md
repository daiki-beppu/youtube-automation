実装計画（`{report:plan.md}`）の要件 ID ごとに、**何をどう検証すれば要件を満たしたと言えるか** を設計してください。**テストコードはまだ書きません**（次の step の担当）。

設計とコードを分ける理由は、テストを先に書くと「書きやすい検証」に引きずられ、要件そのものの検証設計が省略されるためである。ここでは検証の意図だけを固める。

## 手順

1. 実装計画の要件一覧を読み、**要件 ID をそのまま引き継ぐ**（振り直さない）
2. 要件ごとに、それを満たさない実装が確実に落ちるテストケースを設計する
3. 各ケースについて、テスト種別・対象・入力・期待結果・落ちる条件を書く
4. **境界と失敗経路**を明示的に設計する。正常系だけの設計は不合格
5. テストの置き場を決める。テストは **`tests/test_<対象>.py` の pytest** に置く。対象と無関係なファイルへ分散させない
6. モック / フィクスチャの方針を決める。外部 I/O（YouTube API / 生成 AI / ファイルシステム / `op` 等の外部プロセス）の扱いを明記する
7. 検証不能な要件があれば、その理由と代替の検証手段（手動確認手順など）を書く

## テスト種別の選択

| 種別     | 使う場面                                                                       |
| -------- | ------------------------------------------------------------------------------ |
| ユニット | モジュールの関数ロジック、設定 dataclass の組み立て・検証、純粋関数            |
| 統合     | ファイルシステムを跨ぐ処理、複数モジュールの連携、CLI entry point 経由の実行   |
| 契約     | packaging / CLI / skill の規約が守られていること（`yt-*` entry point 登録、SKILL.md frontmatter など） |
| 手動     | 外部サービスの実挙動に依存し自動化できないもの（理由を必ず書く）               |

## 制約

- **1 要件 ID に最低 1 テストケース。** 対応がない要件は「検証不能な理由」を書く。黙って落とさない
- テストは実装の内部構造ではなく **振る舞い** を検証するよう設計する。private 関数を直接叩く設計にしない
- 外部サービス（YouTube API / 生成 AI）への実アクセスをテストに含めない
- `critical regression` の 3 種（①誤公開・誤メタデータ ②データ破壊 ③auth 破壊）に触れる変更なら、その 3 種それぞれに対する回帰テストを必ず設計する
- 実行コマンドは Policy のツールチェーンポリシーに従って記述する

## 判定

- 全要件にテストケースが対応づいた（または検証不能の理由が書かれた）→ 次へ
- 実装計画の要件が曖昧でテスト設計できない → 計画へ差し戻す
