バグの**原因を特定**し、修正方針と回帰テスト設計を作ってください。**この step ではコードを書きません。**

直し方から考え始めないでください。原因が確定していない状態で書いた修正は、症状の出口を塞ぐだけの対症療法になります。

## 手順

### 1. 症状を観測事実として並べる

**この指示に添えられた直前の出力**（intake が作った実装ブリーフ）と issue 本文から、**報告された症状をすべて**列挙する。解釈を混ぜず、観測されたことだけを書く。

**`intake-brief.md` をファイルとして探さないでください。** intake は callable sub-workflow であり、そのレポートは子の report namespace に置かれるため、この step の Report Directory には存在しません（docs/takt-operations.md）。

このとき、以下が揃っているかを確認する:

- **再現条件** — どんな入力・状態・手順で起きるか
- **期待動作** — 本来どうなるべきか
- **実際の動作** — 実際にどうなったか

**揃っていないときは、まず自力で埋める。** issue のコメント、CI のログ、`git log` / `git bisect` 相当の履歴調査、実際にコードを動かしての再現を試みる。埋められた分は出典を明記する。

**調査しても再現条件を確定できず、報告からも読み取れない場合のみ、着手を打ち切る。** 再現できないバグは診断できず、直ったかどうかも判定できない。打ち切るときは、何を試して再現しなかったかを報告に残す。

### 2. 因果を辿る

症状の観測点から入口まで、コードを読んで**逆向きに辿る**。各段を `file:line` で示し、飛ばさない。「このあたりが怪しい」で止めない。

### 3. 対立仮説を潰す

同じ症状を説明しうる**別の原因を最低 1 つ**自分で立て、それを棄却する根拠を示す。棄却できないなら、原因はまだ特定できていない。

棄却の根拠は観測（コードの引用・ログ・実測）に基づくこと。「そちらは考えにくい」は根拠ではない。

### 4. 説明できていない症状を数える

原因仮説が、列挙した症状のうちいくつを説明できるかを表にする。

- 説明できない症状が残る → 原因が複数あるか、特定が誤っている。**どちらなのかを調査する**
- 逆に、原因から導かれるはずの症状が報告にない → 「まだ観測されていないだけ」か「原因が違う」か。どちらなのかを判定する

### 5. 検証可能な予測を書く

「この原因が正しいなら、入力 X で症状 Y が出る」という形の予測を、**再現テストとして書ける粒度**で書く。次の step はこの予測を検証する。

予測が曖昧だと、テストが red でも green でも解釈できてしまい、診断の検証にならない。

### 6. 要件 ID を採番する

修正後に成り立つべきことを要件として採番する（`REQ-<issue番号>-<2桁連番>`）。要件は「症状 S-1 が再現条件下で発生しない」の形で書く。

### 7. 修正方針を決める

因果の連鎖の**どこを断つか**を決める。連鎖の末端（症状の出口）を塞ぐ方針になっていないかを自分で検査し、対症療法でない理由を書く。

### 8. 影響範囲と回帰リスクを洗う

修正箇所に依存している既存の呼び出し元を Grep で列挙し、壊しうる既存挙動を特定する。

### 9. 回帰テストを設計する

- **再現テスト** — 予測 ID に対応させる。修正前は失敗（症状を再現）、修正後は成功
- **既存挙動の回帰** — 影響範囲で洗い出した既存契約を守るケース
- **critical regression** — ①誤公開・誤メタデータ ②データ破壊 ③auth 破壊 に触れる修正なら、3 種それぞれの回帰ケース

配置は対象モジュールごとに `tests/test_<対象>.py` の pytest。

### 10. 規約整合性を事前申告する

修正方針を規約文書と照合し、整合または逸脱を申告する。検査対象は、リポジトリルートの CLAUDE.md、`docs/development.md`、`docs/skill-design/skill-authoring-guidelines.md`、`docs/adr/` の有効 ADR（ADR-0013 = dashboard TS 例外、ADR-0021 = メンテナンスモード）。**バグの原因そのものが規約逸脱だった場合**（設定値のハードコーディング、`load_config` を経由しない設定アクセス、生の `Exception` の catch 等）は、その事実を原因の記述に含める。

## 制約

- **プロダクションコード・テストコードを書かない。** この step の成果物は診断レポートのみ
- 原因を特定せずに修正方針を書かない
- メンテナンスモード（ADR-0021）のゲート外の改善を修正方針に混ぜない
- 診断中に見つけた「今回の修正と因果のない問題」は、その場で直さず「スコープ外の発見」節に記録する（Policy のスコープ外発見ポリシーに従う）

## 判定

**これは {step_iteration} 回目の診断です。やり直しの上限は 3 回です。** `{step_iteration}` が 4 以上なら、内容にかかわらず打ち切ってください。3 回やり直しても原因を確定できないバグは、この workflow で扱える範囲を超えています（docs/takt-operations.md）。

診断のやり直しは 3 方向から来ます — 診断レビューの `NEED_REDIAGNOSE`、再現テストが red にならなかった、修正が対症療法にしかならなかった。**どの経路で戻ってきても同じラウンドに数えます。**

- `{step_iteration}` が 4 以上 → **打ち切る**。棄却された仮説とその根拠、まだ説明できていない症状、決着に必要な情報を報告に残す
- 原因を特定し、予測・修正方針・回帰テスト設計を作った → 診断レビューへ
- 調査しても再現条件を確定できない → 打ち切る。試した再現手順と結果を報告に残す
- 原因が複数あり、1 つの issue として扱うべきでない → 打ち切る。分割の提案を報告に残す

やり直しのときは、**前回の診断レポートを読んでから始めてください。** 棄却済みの仮説を再提出すると、レビューで同じ理由で落ちます。前回何が否定されたかを踏まえて、探索の方向を変えること。
