ゲート段レビュー（feature では設計レビュー、fix では診断レビュー）の指摘を、**レポートを直して** 解消してください。**プロダクションコードは書きません。**

対象は呼び出し元の workflow によって変わります。Report Directory にあるものを直してください。

| workflow           | 直すレポート                 | レビューレポート                      |
| ------------------ | ---------------------------- | ------------------------------------- |
| `auto-feature`     | `plan.md` + `test-design.md` | 設計 / 規約整合性 / テスト設計の 3 種 |
| `auto-fix`         | `diagnosis.md`               | 診断妥当性 / 規約整合性 / テスト設計の 3 種 |
| `auto-maintenance` | `plan.md`                    | リファクタ計画 / 規約整合性の 2 種    |

## 手順

1. Report Directory の設計レビューレポート 3 種をすべて読む
2. `new` / `persists` / `reopened` の全 finding を列挙する。**取捨選択しない**
3. finding ごとに対応方針を決める:
   - **修正する**: 該当する設計レポートを書き換える
   - **修正しない**: 指摘が事実誤認である根拠を、レポートの該当箇所を引用して示す
4. 対象の設計レポートのファイルを直接書き換える
5. 要件 ID は **振り直さない**。要件が分割されたときは枝番（`REQ-55-03a` / `REQ-55-03b`）を足す
6. 規約整合性レビューが NEEDS_CONVENTION_REVISION を出しているなら、設計レポートの「規約整合性の事前申告」に逸脱点・技術的正当性・規約文書の改訂案を追記する（規約文書本体の改訂は実装 step で行う）

## 制約

- **プロダクションコード・テストコードを書かない。** この step で触るのはレポートファイルのみ
- finding を黙って落とさない。修正しないなら理由を書く
- 指摘の解消を装わない。レポートの文言だけ変えて実質が変わっていない修正は、次のレビューで `reopened` になる
- 指摘されていない箇所を、ついでに書き換えない（レビューの差分追跡が壊れる）

## 判定

**これは {step_iteration} 回目のゲート修正です。上限は 3 ラウンドです。** `{step_iteration}` が 4 以上なら、レポートの手直しでは収束していないと判断し、前段（feature なら計画、fix なら診断）へ差し戻してください（docs/takt-operations.md）。

この step にはレビューからだけでなく、feature では `write_tests`（テストを書けない要件が残る）、fix では `reproduce`（再現に環境依存があり決定的なテストにできない）からも入ってきます。この挟み込みで loop monitor の cycle が途切れるため、ラウンド数はこの step 自身が数えます。**どの経路で戻ってきても同じラウンドに数えます。**

- `{step_iteration}` が 4 以上 → 前段へ差し戻す。各ラウンドで直した内容と、残った指摘を報告に残す
- 全 finding に対応（修正 or 反論）した → 設計レビューへ戻る
- 指摘が設計の前提そのものを否定しており、レポート修正では解消できない → 前段へ差し戻す（feature なら再計画、fix なら再診断）

fix では、診断レビューの `NEED_REDIAGNOSE` はこの step を経由しません（原因の特定が誤っているという判定であり、レポートの手直しでは解消しないため）。この step に届く fix の指摘は、記述の不足・根拠の追記で埋まるものだけです。
