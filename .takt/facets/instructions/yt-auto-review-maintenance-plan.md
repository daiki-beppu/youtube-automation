**リファクタリング計画の妥当性** をレビューしてください。まだコードは変更されていません。維持契約の見落としをここで見つけることは、実装後に見つけるより桁違いに安い — それがこの step の役割です。

他のレビュアーの有無を前提にしないでください。規約整合性はこのレビューの担当外です。

## 手順

1. Report Directory のリファクタリング計画（`{report:plan.md}`）を Read で開く
2. Knowledge の Source Path を Read で開き、全文を取得する
3. 以下の観点で計画を判定する:

| 観点             | 見るもの                                                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 維持契約の網羅   | 計画の維持契約表に漏れがないか。**変更対象モジュールの公開面を自分で実際に走査して照合する** — `pyproject.toml` の entry point、公開関数・クラスの呼び出し元（`rg` で import 元を列挙）、raise される例外型、対象を参照する config・skill・テスト。表にない契約が見つかれば名指しで差し戻す |
| 挙動不変性       | リファクタ方針が外部挙動の変更（CLI の引数・出力、例外型、config の解釈、skill 配布物・ファイル配置の契約）を含んでいないか。「ついでに直す」が方針に紛れていないか                                                                             |
| 動機の実在       | 変更の動機が観測可能な問題（file:line で示せる重複・結合・障害・テスト困難の実例）か。推測の技術的負債（「いずれ問題になりそう」「一般にこうすべき」）が動機になっていないか                                                                   |
| 担保テストの対応 | 各契約の担保テスト欄が実在するか（パスを確認する）。「実在」と書かれたテストが本当にその契約を検証しているかを抜き取りで確認する。無い契約に「なし → safety_net で追加」が漏れなく記録されているか                                             |
| 分割可能な大きさ | 1 PR でレビューできる大きさか。大きすぎるなら、どこで分割できるかを示して差し戻す                                                                                                                                                              |

**これは {step_iteration} 回目のレビューです。** 再走査の対象は **計画全体（維持契約表の全行 × 上表の全観点）** です。Policy の再走査ポリシーと収束ポリシーに従ってください（2 回目以降の新規指摘は、計画の無効化を観測で示せるものだけがブロッキング）。

## 判定（3 値）

- **NEED_REPLAN** — 計画の前提そのものが誤っている: 対象が既に壊れている（リファクタリングではなくバグ修正が必要）、動機とされた問題が実在しない（走査しても観測できない）、目的が挙動変更なしには達成できない
- **REJECT** — ブロッキングの `new` / `persists` が 1 件以上: 維持契約の漏れ、外部挙動の変更を含む方針、担保テストの誤対応。指摘には走査結果の根拠（file:line）を必ず付ける
- **APPROVE** — ブロッキング指摘なし（非ブロッキング指摘が残っていてもよい）

## 禁止

- コードを書くこと（指摘と修正案の提示のみ）
- 規約文書の条文の引用による指摘（規約整合性レビュアーの担当。ここでは計画としての妥当性のみを見る）
- 自分の走査結果を示さずに「漏れがありそう」と指摘すること（網羅の指摘は、漏れた契約の名指しと根拠が義務）
- より広いリファクタの提案（スコープの拡大はこのレーンの規律に反する。気づきは「非ブロッキング指摘」へ記録する）
- 曖昧な指摘（「もう少し慎重に」等）
