リファクタリングに入る前の**命綱**を張ってください。計画（`{report:plan.md}`）の維持契約それぞれについて担保テストの存在を確認し、無いものには characterization テスト（現在の挙動をそのまま固定するテスト）を追加し、リファクタ前の時点で全てが green であることを確認します。**プロダクションコードは変更しません。**

テストのないコードを動かすのは、命綱なしで構造を組み替えるのと同じです。この step の完了時点で「契約が守られていることは pytest が検証できる」状態を作ります。

## 手順

1. 計画の維持契約表を読み、契約ごとに処理する
2. **担保テストありの契約**: そのテストを Read で開き、本当にその契約（引数・出力・例外型・スキーマ）を検証しているかを確かめる。名前だけ関連していて実質を検証していないテストは「なし」として扱い、3 へ
3. **担保テストなしの契約**: characterization テストを追加する
   - **現在の挙動を観測してから書く。** 実際に関数を呼び・CLI を実行し、いま返る値・いま送出される例外をそのまま期待値として固定する
   - **望ましい挙動への先回りは禁止。** 現在の挙動が奇妙に見えても、現在の挙動を固定する（挙動を変えるのはこのレーンの仕事ではない）。仕様として誤っていると確信する挙動を見つけたら「スコープ外の発見」節に記録したうえで、テストは現在の挙動のまま固定する
   - characterization テストは**書いた時点で green でなければならない**。red になるなら、現在の挙動を写せていないか、対象が壊れている
   - 置き場は `tests/test_<対象>.py`（pytest）。対応する要件 ID をコメント・関数名・docstring で埋め込む:
     ```python
     # REQ-55-01: リファクタ後も yt-xxx の出力形式が変わらない
     def test_xxx_output_format_is_stable():
         ...
     ```
   - 外部サービス（YouTube API / 生成 AI / `op` 等の外部プロセス）へ実アクセスしない。外部 I/O はモックする
4. **green の確認**: テスト全体を実行し、リファクタ前の時点で全て green であることを確認する:
   ```
   nix develop --command uv run pytest
   ```
   **既存テストが red なら対象は壊れている。** characterization の追加ではなくバグ修正が必要であり、このレーンの対象外（下記判定で ABORT）
5. 契約 ↔ テスト（要件 ID）の対応と実行結果をレポートに記録する。既存テストで担保した契約は、そのテストのパスを根拠として書く

## 制約

- **プロダクションコード（`src/youtube_automation/` 等）を変更しない。** この step で書くのはテストのみ。「テストしやすくするための小さな変更」も禁止 — それはリファクタ本体の仕事であり、変更前の挙動を固定するというこの step の目的と矛盾する
- 計画の維持契約表にない契約のテストを勝手に追加しない。走査で表の不足を見つけたら、計画の修正へ差し戻す

## 判定

- 全維持契約にテスト（既存 or 今回追加）が対応し、リファクタ前の green を確認した → リファクタ実装へ
- 既存挙動のテストが修正前から red である（対象が既に壊れている）→ **ABORT**。どのテストがどう失敗したかを報告に残す（auto-fix へ回す）
- 計画の維持契約リストに誤り・不足がある（実在しない契約が書かれている / 走査で表にない契約が見つかった）→ 計画修正へ差し戻す
