**テスト設計の妥当性** だけをレビューしてください。まだテストコードは書かれていません。「この設計どおりにテストを書けば、要件を満たさない実装が確実に落ちるか」を判定します。

他のレビュアーの有無を前提にしないでください。アーキテクチャ・規約整合性はこのレビューの担当外です。

対象は呼び出し元の workflow によって変わります。Report Directory にあるものを読んでください。

| workflow       | 要件一覧の出どころ            | テスト設計の出どころ                  |
| -------------- | ----------------------------- | ------------------------------------- |
| `yt-auto-feature` | `plan.md` の「要件一覧」      | `test-design.md`                      |
| `yt-auto-fix`     | `diagnosis.md` の「要件一覧」 | `diagnosis.md` の「回帰テスト設計」節 |

## 手順

1. 要件一覧とテストケースの対応表を Read で開いて突き合わせる
2. **トレーサビリティの検証**: 要件 ID が 1 件残らずテストケースに対応しているか。対応がない要件に「検証不能な理由」が書かれているか
3. **検出力の検証**: 各ケースの「このケースが落ちる条件」を読み、そのケースが通っても要件を満たさない実装が書けてしまわないかを考える。**通るだけで意味のないテストを見逃さない**
4. **境界・失敗経路の検証**: 正常系だけになっていないか。不正入力（設定キーの欠落・型不一致）・I/O 失敗・空入力・境界値が設計されているか
5. **critical regression の検証**: ①誤公開・誤メタデータ ②データ破壊 ③auth 破壊 に触れる変更なら、3 種それぞれの回帰ケースが設計されているか
6. **配置の検証**: テストが `tests/test_<対象>.py`（pytest）の規約に沿って配置されているか
7. **外部依存の検証**: 外部サービスへの実アクセスが設計に含まれていないか。モック方針が具体か
8. **fix のときのみ — 再現テストの検証**: 各再現テストが診断の「検証可能な予測」（予測 ID）と対応づいているか。**修正前に red になる条件**が書かれているか。green にしかならないテストは、修正が効いたことを示せないため差し戻す
9. **fix のときのみ — 既存挙動の回帰の検証**: 診断の「影響範囲と回帰リスク」で洗い出された既存契約が、それぞれ回帰ケースで守られているか。洗い出しはあるのにケースがない契約は差し戻す

**これは {step_iteration} 回目のレビューです。** 再走査の対象は **要件 ID ↔ テストケース対応表の全行**です。Policy の再走査ポリシーと収束ポリシーに従ってください（2 回目以降の新規指摘は、検出力の欠陥など設計の無効化を反例で示せるものだけがブロッキング）。

## 差し戻す条件

- 要件 ID に対応するテストケースがなく、検証不能の理由も書かれていない
- ケースの期待結果が「エラーにならないこと」だけで、正しさを判定していない
- 実装の内部構造（private 関数・内部状態）に依存した設計になっている
- モック方針が「適宜モックする」等、実装者が判断を迫られる粒度で止まっている
- critical regression に触れる変更で回帰ケースが欠けている
- （fix）再現テストに対応する予測 ID がない、または修正前に red になる条件が書かれていない
- （fix）診断が挙げた既存契約に、対応する回帰ケースがない

## 禁止

- テストコードを書くこと（この step はレビューのみ）
- 「カバレッジ N% 以上」のような、要件と結びつかない数値基準での指摘
- 設計されていないテストの追加を、根拠なく要求すること（要求するなら、どの要件がカバーされていないかを示す）
