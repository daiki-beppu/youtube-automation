直前の intake が出力した**実装ブリーフ**を読み、文書・スキル変更の計画を立ててください。ブリーフは**この指示に添えられた直前の出力**として渡されています。**`intake-brief.md` をファイルとして探さないでください** — intake は callable sub-workflow であり、そのレポートは子の report namespace に置かれるため、この step の Report Directory には存在しません（docs/takt-operations.md）。**この step ではファイルを変更しません。**

このレーンは docs / SKILL.md / CLAUDE.md など**文書・スキル限定の軽量レーン**です。フル設計ゲートとテスト先行を持たない代わりに、入口のこの検査でレーン違いを確実に止めます。プロダクションコードの変更が 1 ファイルでも必要なら、このレーンでは扱いません。

## 手順

1. **ブリーフの読み込み**: ブリーフの「確定している決定」「要件候補」「対象外」「制約」を読む。ブリーフに書かれていない要求を足さない
2. **レーン適合の検査**: 要件候補を満たすために変更するファイルをすべて列挙し、1 つずつ分類する
   - **このレーンで扱える**: `docs/`、`README.md`、`CLAUDE.md`、`.claude/skills/`、`.claude/CLAUDE.template.md`、`examples/` の文書・スキル・設定例。および文言を担保する契約テストの追随（`tests/` のみ）と、changelog ゲートに伴う `CHANGELOG.md` の追記
   - **扱えない（プロダクションコード）**: 上記以外すべて。特に `src/youtube_automation/`、`dashboard/`、`extensions/`、`pyproject.toml`、`.github/`。1 つでも変更が必要なら **ABORT** し、回すべきレーン（機能追加なら auto-feature、不具合修正なら auto-fix）を報告する
3. **要件 ID の採番**: 要件候補に `REQ-<issue番号>-<2桁連番>` を振る。Policy の採番規則に従う。ここで振った ID は後段で不変
4. **契約テストの確認**: 変更する文言・コマンド・パスを担保する契約テストの有無を grep で確認する。文書の記述は `tests/test_*_contract.py` / `tests/test_*_docs.py` / `tests/test_skill_docs_consistency.py` 等が機械担保していることがある。変更対象のファイル名・見出し・コマンド文字列で `rg -l <文字列> tests/` を引き、追随が必要なテストを要件 ID ごとに列挙する。担保するテストが無い要件も「なし」と記録する（後段の検査が「確認漏れ」と「確認の結果なし」を区別できるように）
5. **変更方針**: 要件 ID ごとに、変更対象ファイルと変更内容を書く。skill を変更するなら `docs/skill-design/skill-authoring-guidelines.md` の必須 3 点（不可逆・外部反映操作の承認ゲート / 前提の存在ガード / 配布先で解決できる参照）と frontmatter 規約（`description:` は double-quoted）に触れるかを確認する
6. **影響範囲の洗い出し**: 変更する文書を参照している他文書・skill を `rg` で洗い出し、相互矛盾が生まれないか（CLAUDE.md ↔ docs/ ↔ SKILL.md で同じ事実が食い違わないか）を確認する

## 制約

- ファイルを変更しない（計画レポートの出力のみ）
- 契約テストの緩和・削除を方針にしない。テスト追随とは**文言の同期**である
- ブリーフの未決事項を自分の判断で埋めない

## 判定

**これは {step_iteration} 回目の計画です。作り直しの上限は 3 回です。** `{step_iteration}` が 4 以上なら、内容にかかわらず打ち切ってください。

計画のやり直しは複数方向から来ます — 実装（`implement`）が計画の前提の誤りを検出した、文書レビューの修正（`docs_fix`）が上限に達した・指摘が計画の前提を否定した、`spillover` が因果ありの発見を引き戻した、loop monitor の判定。**どの経路で戻ってきても同じラウンドに数えます。**

- `{step_iteration}` が 4 以上 → **打ち切る**。各ラウンドで立てた方針と差し戻された理由を報告に残す
- 変更対象がすべて文書・スキルであり、要件 ID を採番し変更方針を決めた → 次へ
- ユーザーが質問をしている（実装タスクではない）→ 完了
- プロダクションコードの変更が必要 → **ABORT**。必要なコード変更と、auto-feature / auto-fix のどちらへ回すべきかを報告に残す
- ブリーフの決定だけでは方針が一意に決まらない → ABORT し、何が決まれば進めるかを列挙する

やり直しのときは、**前回の計画レポートを読んでから始めてください。** 同じ方針を言い換えて再提出すると、同じ理由で差し戻されます。前回何が否定されたかを踏まえて方針を変えること。
