承認された診断（`diagnosis.md`）の回帰テスト設計に従って、**修正前にテストを書いて**ください。

この step の目的はテストを揃えることだけではありません。**再現テストが red になることが、診断した原因が正しいことの証拠**になります。red にならなければ、原因の特定が誤っています。

## 手順

1. 診断レポートの「回帰テスト設計」を読む。**設計にあるケースをすべて実装する**（取捨選択しない）
2. 「テストファイル配置」に従ってファイルを作る。対象モジュールごとに `tests/test_<対象>.py` の pytest
3. 各テストに、対応する要件 ID・ケース ID・予測 ID を埋め込む:
   ```python
   # REQ-55-01 / TC-01 / P-1
   def test_benchmark_collect_excludes_videos_below_min_views():
       ...
   ```
4. テストを実行する:
   ```
   nix develop --command uv run pytest
   ```
5. **結果を種別ごとに検証する**:

   | テスト種別                   | 期待する結果                      | 違ったときの意味                       |
   | ---------------------------- | --------------------------------- | -------------------------------------- |
   | 再現テスト（予測 ID を持つ） | **red**（症状を再現して失敗する） | green なら診断が誤り。差し戻す         |
   | 既存挙動の回帰               | **green**（修正前から通る）       | red なら既存挙動の把握が誤り。差し戻す |
   | critical regression 回帰     | green                             | red なら既に壊れている。診断へ戻す     |

6. 再現テストが red のとき、**失敗の内容が予測と一致しているか**を確認する。「何かのエラーで落ちた」では不十分。診断の予測 P-x が「入力 X で症状 Y」と書いているなら、症状 Y として落ちていること

## 制約

- **プロダクションコードを直さない。** この step で書くのはテストのみ
- 再現テストを green にするために期待値を書き換えない。red のまま次へ渡す
- 外部サービス（YouTube API / 生成 AI）へ実アクセスしない。診断のモック方針に従う
- 設計にないテストを追加しない。必要だと考えるなら、理由を報告に書いて診断へ差し戻す

## 判定

**ラウンド上限は 3 回です。** `{step_iteration}` が 4 以上なら、内容にかかわらず打ち切ってください。3 回書き直しても症状を再現できないバグは、この workflow で扱える範囲を超えています。

- `{step_iteration}` が 4 以上 → **打ち切る**。各ラウンドで何を書き、どう失敗したかを報告に残す
- 再現テストが red、既存挙動の回帰が green → 修正へ
- **再現テストが green（症状を再現できない）→ 診断へ差し戻す。** テストの書き方の問題ではないかを一度確認したうえで、原因の特定が誤っている可能性として報告する
- 再現テストは red だが、**失敗の内容が予測と違う** → 診断へ差し戻す。何を予測し、実際に何が起きたかを対比して報告する
- 再現に環境依存（時刻・ネットワーク・実行順）があり、決定的なテストにできない → 診断レビュー指摘の解消へ戻し、テスト設計の見直しを求める
- 既存挙動の回帰テストが修正前から red → 診断へ差し戻す。既存挙動の把握が誤っているか、別のバグが同時に存在する

**症状を再現しないテストを抱えたまま修正へ進んではいけません。** 再現テストが red でなければ、修正が効いたかどうかを判定する手段がありません。
