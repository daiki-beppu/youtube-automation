変更された文書が **実装・実態と一致しているか** をレビューしてください。文書は書いた時点から腐り始めます。この step の役割は、書かれた記述が現在のリポジトリの事実と一致していることを、記憶ではなく照合で確かめることです。

他のレビュアーの有無を前提にしないでください。規約準拠（skill-authoring-guidelines / frontmatter 等）はこのレビューの担当外です。

## 手順

1. 文書変更計画（`{report:docs-plan.md}`）の要件一覧を読み、今回の累積差分（変更された文書・テスト）をすべて Read で開く
2. 以下の観点で、変更された記述を 1 つずつ実態と照合する:

| 観点               | 照合方法                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 記載コマンドの実在 | 文書に書かれたコマンド（`yt-*` CLI / `uv run ...` / スクリプトパス）が実在するか。`pyproject.toml` の `[project.scripts]`・該当スクリプトと突き合わせる      |
| 実行例の整合       | 実行例の引数・フラグ・値が現在の実装（`argparse` の定義・`choices=`）で受理されるか                                                                          |
| パス参照の解決     | 文書内のファイルパス・相対リンクが実在するか（リンク切れ）。リンク先の該当節が実在するか                                                                     |
| 文書間の相互矛盾   | 同じ事実の記述が CLAUDE.md ↔ docs/ ↔ SKILL.md で食い違っていないか（変更した側だけ直り、参照する側が古いままのケース）                                       |
| 契約テストとの整合 | 変更した文言を担保する契約テストが同期されているか。計画の「担保する契約テスト」列と実際の差分を突き合わせ、変更した文言を `rg` で検索して取りこぼしを探す   |
| 実態との一致       | 記述された挙動・設定キー名・ファイル構成が実装の現状と一致するか                                                                                             |

3. 要件 ID 単位で充足を判定する。ID をまたいだ「おおむね一致している」判定を出さない

**これは {step_iteration} 回目のレビューです。** Policy の収束ポリシーに従ってください。2 回目以降の新規指摘は、記述が読者を実際に誤らせること（存在しないコマンド・解決しないパス・矛盾する記述）を file:line で示せるものだけがブロッキングです。

## 指摘の義務

すべての指摘に **file:line と根拠**（実在しないことを示す照合結果、矛盾する 2 箇所の引用、同期されていない契約テストの該当行）を付けてください。付けられない指摘は無効です（`finding_id` を発行しない）。

## 判定（2 値）

- ブロッキングの `new` / `persists` が 1 件以上 → REJECT
- ブロッキング指摘なし → APPROVE（非ブロッキング指摘が残っていてもよい）

## 禁止

- ファイルを変更すること（指摘と修正案の提示のみ）
- 規約文書の条文の引用による指摘（規約・品質レビューの担当。ここでは事実との一致だけを見る）
- 文体・言い回しの好みの指摘（読者を誤らせる実害を説明できないもの）
- 曖昧な指摘（「もう少し正確に」等）
