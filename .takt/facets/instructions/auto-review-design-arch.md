**実装計画の設計としての妥当性** をレビューしてください。まだコードは書かれていません。実装に入る前に、構造の誤りを止めるのがこの step の役割です。

他のレビュアーの有無を前提にしないでください。規約整合性とテスト設計はこのレビューの担当外です。

## 手順

1. Report Directory の実装計画（`plan.md`）を Read で開く。intake が確定した決定・制約・対象外は、その「ブリーフからの引き継ぎ」節にある。**`intake-brief.md` をファイルとして探さないでください** — intake は callable sub-workflow であり、そのレポートはこの step の Report Directory には存在しません（docs/takt-operations.md）
2. Knowledge の Source Path を Read で開き、全文を取得する。`##` セクションをすべて列挙し、取捨選択しない
3. 列挙した各セクションの判定基準を実装方針と照合する
4. 以下の観点で設計を判定する:

| 観点         | 見るもの                                                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 要求の充足   | 要件 ID ごとの方針が、その要件を実際に満たすか。方針が抽象すぎて実装が一意に決まらない箇所はないか                                           |
| 責務の配置   | 業務ロジックが `youtube_automation` パッケージ側にあり、CLI entry point / skill script が薄いままか。責務の置き場が既存構造（configuration / infrastructure / 各ドメインモジュール）に合っているか |
| データの流れ | 入出力の型が決まっているか。新しく置く設定・データの SSOT（`config/channel/*.json` / collections / レポート）が明示されているか              |
| 失敗の設計   | 失敗経路が設計されているか。エラーがドメイン例外（`infrastructure/errors.py`）で設計され、生の `Exception` / `KeyError` を catch しない形になっているか |
| 変更の広がり | 1 要件の実装が想定外に多くのファイルへ波及していないか。波及するなら、その必然性が説明されているか                                           |
| 未来への負債 | いま入れると後で剥がしにくくなる構造（暗黙の状態・グローバル・双方向依存）がないか                                                           |

**これは {step_iteration} 回目のレビューです。** 再走査の対象は **実装計画全体**（全要件 ID の方針 × 上表の全観点）です。Policy の再走査ポリシーと収束ポリシーに従ってください（2 回目以降の新規指摘は、設計の無効化を示せるものだけがブロッキング）。

## 差し戻す条件

- 要件 ID に対応する方針が「〜を実装する」で止まり、どう実装するかが決まっていない
- 業務ロジックが CLI entry point / skill script 側へ置かれている
- 新しく置く設定・データの SSOT が特定されていない（チャンネル固有値が `config/channel/*.json` へ集約されていない）
- 失敗経路が設計されていない（正常系のみの方針）
- 1 要件の実装が、必然性の説明なく多数のファイルへ分散する設計になっている

## 禁止

- コードを書くこと（指摘と修正案の提示のみ）
- 曖昧な指摘（「もう少し整理して」等）
- 規約文書の条文の引用による指摘（規約整合性レビュアーの担当。ここでは設計としての妥当性のみを見る）
- 設計・構造への影響を説明できない好みだけの指摘
