# 要件トレーサビリティポリシー

issue の要求が、計画 → テスト設計 → 実装 → レビューの各段で失われていないことを、**要件 ID** で機械的に追跡可能にする。

## 要件 ID の形式

```
REQ-<issue番号>-<2桁連番>    例: REQ-55-01
```

- issue 番号は intake が確定した linked issue の番号。intake は issue を確定できない実行を `blocked` にするため、issue に紐づかない採番は起こらない
- 連番は計画 step が採番した順に固定する。**後段で振り直してはならない**（振り直しは追跡の断絶になる）
- 要件が分割されたときは `REQ-55-03a` / `REQ-55-03b` のように枝番を足す。既存 ID を潰さない

## 各段の義務

段の名前は workflow によって変わるが、義務は同じ。

| 段（feature / fix）         | 義務                                                                                                                  |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| intake                      | issue の受け入れ条件（fix では報告された症状）を要件候補として抽出し、抜けなく列挙する                                |
| 計画 / 診断                 | 要件 ID を採番し、要件 → 実装方針（fix では修正方針）の対応表を出す。ID なしの要件を残さない                          |
| テスト設計 / 回帰テスト設計 | 要件 ID → テストケースの対応表を出す。**1 要件に最低 1 テストケース**。対応がない要件は「テスト不能な理由」を明記する |
| 実装 / 修正                 | 実装した要件 ID を宣言する。宣言にない変更は scope 外として理由を書く                                                 |
| レビュー                    | 要件 ID 単位で充足を判定する。ID をまたいだ「おおむね満たしている」判定を出さない                                     |

fix では、**報告された症状が 1 つ残らず要件 ID を持つ**こと。症状 → 要件 ID → 再現テストケースが繋がっていない症状は、直ったかどうかを判定できない。

## 判定規則

- **未着手の要件 ID が 1 件でも残っていれば承認しない。** 対応しない判断をした要件は、ID を残したまま「対応しない理由」を記録する（黙って消さない）
- 受け入れ条件に書かれていない機能を足していたら、スコープ超過として指摘する。良かれと思った追加も対象
- 要件 ID とテストケースが 1 対 1 で対応していないとき、その要件は「検証されていない」と扱う
- 「実装した」の根拠は差分の該当箇所（`file:line`）。テストの通過だけを根拠にしない

## 禁止

- 要件 ID を持たない受け入れ条件を残したまま次の段へ進むこと
- レビューで要件表を再構成すること（採番は計画段で確定。レビューは照合のみ）
- 「後で対応」を理由に要件を表から落とすこと（残す場合は issue 化して番号を記録する。起票の手順はスコープ外発見ポリシーに従う）
